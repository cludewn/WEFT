# タイムゾーンと日時指定

[ホーム](Home-ja) · [コマンド一覧](Command-Reference-ja) · [トラブルシューティング](Troubleshooting-ja) · [English](Timezones-and-Scheduling)

予約を作る前に、時刻をどのように解釈するかを決めます。`2h`などの相対指定は経過時間を表し、現地の日付や毎日の時刻にはタイムゾーンが必要です。

<a id="choose-time-input"></a>

## 経過時間と現地日時を選ぶ

| 目的                        | 指定する引数                                                         | 時刻の解釈                                                 |
| --------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------- |
| フォーム送信の2時間後に投稿 | `/message schedule create`：`after`に`2h`を入力                      | フォーム送信と直前確認の後から2時間を計測します。          |
| 指定した現地日時に投稿      | `/message schedule create`：`at`に`2026-11-01 19:30`を入力（書式例） | WEFTの現在の既定タイムゾーンで、その現地日時を解釈します。 |
| 2時間後にスレッドをクローズ | `/thread close-after`：`after`に`2h`を入力                           | 相対時間だけを指定できます。`at`は使えません。             |

`at`を使う場合は、入力前に[サーバーの既定値](#set-and-check-timezone)を確認してください。日付は書式の例なので、実際には範囲内の有効な未来の日時を選んでください。Discordの引数欄へ引用符なしで入力します。`after`の`1d`の1日は経過時間で24時間です。

単発の予約投稿は、次のように保存して日時を確認します。

1. [`/message schedule create`](Commands-Message-ja#message-schedule-create)を選び、上の表に従って`after`と`at`の**どちらか1つだけ**入力します。もう一方は指定しません。
2. コマンドを実行し、内容フォームを送信して予約を保存します。返された予約IDと送信日時を控えます。
3. 同じチャンネルで[`/message schedule status`](Commands-Message-ja#message-schedule-status)を選び、`id`にその実際の予約IDを入力して実行します。保存された送信日時と状態を確認します。予約の保存は、投稿の送信成功を意味しません。

スレッドのクローズは、[予約クローズ](Scheduled-Thread-Close-ja)に従い、対象スレッド内で作成・確認してください。

`at`を使う場合、単発作成はフォームを開く時点ではなく送信処理中、日時変更はその操作中に既定値を読みます。保存した単発予約は固定の実行日時を保持し、その後の既定値変更では移動しません。

<a id="set-and-check-timezone"></a>

## WEFTのタイムゾーンを設定して確認する

**IANAタイムゾーン**は、`Asia/Tokyo`や`America/New_York`など、地域の時刻規則を表す名前です。WEFTの既定値は`UTC`で、サーバーごとに保存します。変更には「サーバーの管理」権限が必要です。

1. [`/config show`](Commands-Config-ja#config-show)を引数なしで実行し、**WEFTの既定タイムゾーン**を確認します。目的の地域と一致していれば変更は不要です。
2. 変更する場合は[`/config timezone`](Commands-Config-ja#config-timezone)を選び、`value`に`Asia/Tokyo`を入力して実行します。
3. 保存済み・変更なしの応答を読み、もう一度`/config show`を実行して保存値を確認します。

Discordクライアントの表示設定ではなく、WEFTの設定です。有効な別名は使用できますが、`+09:00`のような数値オフセットは使用できません。応答のDiscordタイムスタンプは各閲覧者のタイムゾーンで表示されるため、入力に使った地域と表示が異なる場合があります。

<a id="recurring-local-time"></a>

## 定期投稿の現地時刻を指定する

東京時間で毎日09:30に投稿する例です。

1. 投稿先で[`/message schedule recurring-create`](Commands-Message-ja#message-schedule-recurring-create)を選びます。`frequency`で「毎日」（値: `daily`）を選び、`time`に`09:30`、`timezone`に`Asia/Tokyo`を入力します。`weekdays`は指定しません。
2. コマンドを実行し、内容フォームを送信して、返された予約IDと初回の送信日時を控えます。
3. 同じチャンネルで[`/message schedule status`](Commands-Message-ja#message-schedule-status)の`id`にその予約IDを指定して実行します。保存された現地時刻・タイムゾーン・現在の実行回の予定日時を確認します。

dailyでは曜日を省略します。weeklyでは`mon,tue,wed,thu,fri,sat,sun`から1つ以上を重複なしでカンマ区切りにし、各曜日名の大文字・小文字と前後の空白は区別しません。時刻は24時間表記の厳密な`HH:MM`です。現地の暦上の日付で進み、24時間・168時間の固定加算ではありません。

| 操作               | タイムゾーン省略時                   | 以後のサーバー既定値変更の影響         |
| ------------------ | ------------------------------------ | -------------------------------------- |
| 定期投稿の作成     | フォーム送信時の既定値を保存します。 | 保存済みのタイムゾーンは変わりません。 |
| 繰り返し設定の編集 | 定期投稿の保存値を保持します。       | 新しい既定値へ切り替えません。         |

準備済みの実行回の日時は固定です。以後の準備には、現在のタイムゾーンデータと保存済みの繰り返し設定を使います。

<a id="timing-is-eligibility-not-a-guaranteed-second"></a>

## 保存日時と遅延時の扱いを確認する

予約投稿は、前述のstatusで保存日時が意図した時刻と一致するか確認します。Discordの表示と異なる場合は、閲覧者の表示タイムゾーンとWEFTの入力用タイムゾーンを区別してください。予定日時は実行可能となる境界であり、正確な秒の実行保証ではありません。

[予約投稿](Scheduled-Messages-ja#late-work-restart-and-retries)には境界を含む単発60分・定期の直近未実行回15分の猶予があり、定期の安全な再試行は別途、初回試行から15分です。[予約クローズ](Scheduled-Thread-Close-ja)には投稿の猶予を適用しません。起動時復旧、定期確認、API待機、権限変更に左右されます。不確定・遅延した処理の対処として重複作成しないでください。

<a id="relative-or-absolute-one-time-time"></a>

## 単発入力の正確な規則

[`create`](Commands-Message-ja#message-schedule-create)と[`reschedule`](Commands-Message-ja#message-schedule-reschedule)では、`after`と`at`のどちらか1つだけ指定します。両方・両方なし・空の値はいずれも無効です。

| 指定する引数 | 使用できる形式                                                                                                         | 拒否される例・条件                                                                      |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `after`      | 正の整数と`m`・`h`・`d`のいずれかを1組で指定します。前後の空白と単位の大文字・小文字は正規化します。                   | 複数の単位を組み合わせた`1h30m`、小数、0、先頭0の数値                                   |
| `at`         | ASCII 16文字の`YYYY-MM-DD HH:mm`形式で指定します。各桁を0埋めし、半角空白1つ、24時間表記の`00:00`～`23:59`を使います。 | 前後空白、`T`、秒、小数、`Z`、オフセット、タイムゾーン注記、不正な暦日、DSTの欠落・重複 |

時刻が確定した時点から1分後～365日後（1日は24時間）の範囲で、両端を含みます。暦上の1年ではありません。`at`の差は分単位の整数でなくてもよく、分単位で指定した日時が現在から90秒後なら、有効な場合があります。不正な日付は繰り越さず拒否します。

単発は変換後の固定の実行日時だけを保存します。[`close-after`](Commands-Thread-ja#thread-close-after)は`after`専用で、同じ1m～365dの経過時間範囲です。

<a id="dst-gaps-and-overlaps"></a>

## 夏時間（DST）の欠落・重複を理解する

地域によっては時計を進めたり戻したりします。存在しない現地時刻を**欠落（gap）**、同じ現地時刻が2回現れることを**重複（overlap）**と呼びます。WEFTは単発と定期で扱いを分けます。

| 状況                           | 単発予約の`at`                                                     | 定期投稿                                                              |
| ------------------------------ | ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| 時計が進み指定時刻が存在しない | DST_GAPとして拒否されます。別の時刻を選んでください。              | その回をスキップし、DST_GAP_SKIPPEDを記録します。時刻はずらしません。 |
| 時計が戻り同じ時刻が2回ある    | DST_OVERLAPとして拒否されます。別の時刻か`after`を使ってください。 | 先に到来する日時だけを使います。                                      |

例えば`America/New_York`の`2026-03-08 02:30`は欠落、`2026-11-01 01:30`は重複です。DSTの説明用の例であり、実際の予約には範囲内の有効な未来の日時が必要です。

毎日09:30の定期投稿はDST後も現地09:30なので、前回との間隔が24時間とは限りません。`after`の`1d`は常に経過時間で24時間です。1時間以外の変更がある地域も同じ方針です。タイムゾーンデータはレビュー済みの実行環境更新で保守してください。
