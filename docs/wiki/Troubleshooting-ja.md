## 実際に確認できる情報を区別する

最初にコマンドの応答と、実際のDiscord上の対象を確認します。保存設定や予約情報は、次の表示用コマンドで確認できます。それぞれの権限は必要です。また、現在値を表示するだけで、結果不明だった要求の履歴まで確認できるわけではありません。

| 調べたいこと                           | 使用できる確認方法と限界                                                                                                                                                                                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 保存された設定                         | 「サーバーの管理」権限で`/config show`や各機能の`show`を使います。現在値だけでは、以前のどの要求で保存されたかは判断できません。                                                                                                                                   |
| スレッドの設定・現在の予約クローズ     | 「スレッドの管理」権限で、**対象スレッド内**から`/thread status`を実行します。未完了のクローズ・状態反映すべてや、終了済み予約の履歴は表示しません。                                                                                                               |
| 予約投稿の保存情報                     | 元のチャンネルで「メッセージの管理」権限を使い、`/message schedule list`・`/message schedule status`と予約IDで調べます。本文や、定期投稿の全送信履歴は表示しません。                                                                                               |
| 保存されたメッセージ内容               | 編集可能な場合は、メッセージIDで`/message edit`、予約IDで`/message schedule edit`を開き、**フォームを送信せずに**入力済みの内容を読みます。開くだけでは変更しません。拒否・取得不能は、記録が存在しない証明にはなりません。Discord上の実際の投稿は別に確認します。 |
| ホスト運用者だけが調べられる処理・履歴 | [アプリのログ](Operations-ja#inspect-operation-logs)と[DBの監査記録](Audit-and-Privacy-ja#audit-storage-reference)です。Discordに監査履歴全体の閲覧機能はありません。ホスト・DBへアクセスできない場合は、応答・ID・日時を控えて運用者へ調査を依頼します。          |

これらの確認でも前回の結果を確定できない場合、変更を止めたまま調査します。現在値の一致、ログがないこと、予約が見当たらないことだけで、再送・削除・再クローズを安全とは判断できません。

<a id="automatic-close-not-running"></a>

## 自動クローズを設定したのにスレッドが開いたままです

**考えられる原因:** 親チャンネルの無効、個別除外、記録上の無投稿期間の不足、予約クローズの優先、現在のDiscord状態や権限による実行不可です。期間を設定するだけでは、親チャンネルは有効になりません。

**確認と対処の手順:**

1. [`/config auto-close show`](Commands-Config-ja#config-auto-close-show)を引数なしで実行し、無投稿期間、ボット投稿の扱い、有効な親チャンネルを確認します。親は最大25件と残件数を表示するため、表示にないだけで無効とは判断できません。
2. 該当スレッド内で[`/thread status`](Commands-Thread-ja#thread-status)を引数なしで実行し、そのスレッドに自動クローズが適用されるかどうか、親の設定、個別除外を確認します。親が無効なら、[設定手順](Automatic-Close-ja#enable-a-parent-then-exempt-individual-threads)に従って正しいチャンネルを有効にしてください。意図しない除外は`/thread track`で解除し、statusで再確認します。trackでは無効な親を有効にできません。
3. 記録した活動時刻または計測開始時刻と、現在の無投稿期間を照合します。親の有効化、除外解除、開いた状態への復帰の検知で、計測開始時刻が新しくなる場合があります。作成からの経過時間だけでは判断できません。利用者の投稿や、設定で含めたボットの投稿によって記録時刻が進んでいないか確認してください。時刻が未記録なら[計測開始時刻の確認](Automatic-Close-ja#measurement-baselines)へ進み、作成時刻から無投稿期間を推測しないでください。
4. statusの予約クローズ欄を確認します。実行待ち（`ACTIVE`）・実行中（`EXECUTING`）の予約は自動クローズより優先されます。自動クローズ側では取り消しません。予約を取り消す意図がある場合は、別の[予約クローズ取消手順](Scheduled-Thread-Close-ja#cancel-or-close-now)を使用してください。
5. Discord上の実際のアーカイブ・ロック状態と、WEFTの現在のアクセス・「スレッドの管理」権限を確認します。アーカイブ済みなら新たなアーカイブは不要です。ロック中のスレッドはWEFTでクローズできません。ロックを解除する必要がある場合は、権限のある管理者が手動で解除してから再試行してください。
6. 定期確認の間隔を考慮します。初回は起動から5分後、その後は前回の終了から5分後に開始し、Discordの待機でさらに遅れる場合があります。処理がすでに継続中なら、[スレッドの遅延](#thread-delays)を確認してください。

**安全上の注意:** クローズを強制する目的で期間を短くしたり、trackを繰り返したりしないでください。期間の短縮は既存の活動記録へ適用しますが、対象のスレッドでtrackを繰り返しても計測はリセットしません。親の無効化や個別除外でも、開始済みのクローズは強制停止できません。showとstatusは、処理継続中の操作をすべて表示するものではありません。

**解決しない場合:** 親・スレッドのID、statusの応答、確認日時を運用者へ伝え、[アプリのログ](Operations-ja#inspect-operation-logs)で`automatic_close_candidate_execution_failed`の対象、候補ページの取得失敗、スレッドの結果確認の警告を調べます。WEFTは停止中に受信できなかった投稿をすべて補完しません。[活動・計測開始時刻・実行時期](Automatic-Close-ja#what-counts-as-activity)も参照してください。

## 予約投稿が予定どおりに届かない・送信結果が不明です

**考えられる原因:** 予定日時前、タイムゾーンの認識違い、実行登録・APIの遅延、送信不能な対象、猶予超過、取消・失敗、中断・不確定な送信です。

**確認手順:**

1. 元のチャンネルで[`/message schedule status`](Commands-Message-ja#message-schedule-status)を選び、`id`に控えた予約のUUIDを入力して実行します。DiscordのメッセージIDではありません。控えていない場合は、同じチャンネルで`/message schedule list`を引数なしで実行してください。ただし一覧は終了していない予約だけで、消えたことは取消の証明ではありません。
2. 実際の投稿先と、結果の投稿リンクがあればその内容を確認します。statusは現在の存在確認をしません。作成時の保存完了は予約の保存であり、送信完了ではありません。
3. 予定日時、定期投稿の保存タイムゾーン、設定全体・実行回の状態、再試行数を確認します。再試行中の表示日時は元の予定日時です。
4. 対象のアーカイブ状態と、WEFTの現在の閲覧・送信・埋め込み権限を確認します。
5. 停止後は[単発60分・定期15分の猶予](Scheduled-Messages-ja#late-work-restart-and-retries)と照合します。定期は直近の適用可能な未実行回だけを検討し、古い回をすべて再送しません。

**次の行動を選ぶ:**

| 確認した状態・結果                                      | 対処・再試行条件                                                                                                   |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 保存確定・実行登録待ち                                  | WEFTの登録修復を待ちます。別予約の作成は重複につながります。                                                       |
| 実行中・再試行待ち                                      | 観察し、代替送信で競合させません。                                                                                 |
| `SEND_UNCONFIRMED`・`EXECUTION_INTERRUPTED_UNCONFIRMED` | 送信済みの可能性があります。手動の代替作成前にDiscordと運用記録を確認します。                                      |
| 拒否確定・猶予超過                                      | 原因を直し、応答と実際の投稿先を照合して、送信済みの可能性が残っていないことを確認してから代替の予約を作成します。 |
| 投稿はあるが管理登録・結果保存は未確認                  | 再送・削除前に記録と投稿の両方を調べます。                                                                         |

**安全上の注意:** 送信結果が未確認のまま予約を再作成しないでください。実行途中で中断した送信は、再起動後に自動再送しません。正確な秒や厳密な1回限りの送信は保証しません。取消も実行開始済みの外部送信を強制停止できません。

**解決しない場合:** 手動の代替作成を止め、予約・実行回ID、日時、結果コード、実際の投稿の根拠を運用者が照合します。失敗と推測せず、[送信結果未確認の詳細](Scheduled-Messages-ja#uncertain-sends)を参照してください。

<a id="post-after-recurring-cancel"></a>

## 定期投稿を取り消した後に投稿が届いた

取消が有効になる時点ですでに`EXECUTING`だった実行回は、その後も送信する場合があります。確定した定期投稿の取消は、以後の回を止め、待機中・再試行待ちをスキップします。実行中のDiscord要求の撤回や送信済み投稿の削除は行いません。

1. 取消応答、予約ID、操作日時を保持します。元のチャンネルで[`/message schedule status`](Commands-Message-ja#message-schedule-status)の`id`にそのIDを指定し、取消確定と、競合・`UNCONFIRMED`を区別します。
2. 届いた実際の投稿を確認し、メッセージID・日時を控えます。意図した定期投稿・実行回と照合してください。同じチャンネルの別予約が送る場合もあり、statusは全実行回の履歴を表示するものではありません。
3. 取消が確定し、すでに実行中だった回の投稿だと確認できた場合は、送信を元に戻す目的で予約を再作成したり取消を繰り返したりしません。既存投稿は、権限に応じて[管理メッセージの編集やDiscordでの削除](Managed-Messages-ja#deletion-and-scheduling)で別に管理します。その後も投稿が続く場合や、根拠から送信理由を説明できない場合は、次の変更前に運用者が取消・実行回の監査を照合してください。

後から届いた投稿だけでは、取消が確定した定期投稿の設定が再び有効になったとは判断できません。取消自体が未確認なら、今後の投稿が停止したと判断する前に[結果の見方](#result-states)を確認します。[取消の適用範囲](Scheduled-Messages-ja#cancel-a-reservation)も参照してください。

<a id="thread-open-does-not-unarchive"></a>

## /thread openでアーカイブが解除されません

**最初に確認する原因:** `/thread open`は、Discordですでに開いているスレッドの状態をWEFTへ反映する操作です。WEFTはアーカイブ解除を要求せず、ロック状態も変更しません。

**確認と対処:** Discord上の実際のアーカイブ・ロック状態を確認します。アーカイブ済みの場合は、必要な権限を持つ利用者がDiscord自身の操作で解除してください。ロックされていないスレッドでは、利用者が操作した際にDiscordがアーカイブを解除する場合もありますが、確認せず解除済みと判断しないでください。開いた状態になった後もWEFTの状態反映が必要なら、スレッド内で[`/thread open`](Commands-Thread-ja#thread-open)を引数なしで実行します。

**結果の確認:** コマンドの結果と実際の名前を確認してください。管理記録がある場合、WEFTは該当する保存済みの先頭クローズ用プレフィックスが空でなければ1つだけ除去し、必要に応じて開いた状態を記録します。管理記録のない、対応する開いたスレッドでは変更なしになります。プレフィックス無効でクローズしたスレッドは、名前が変わらない場合があります。自動の状態反映がすでに完了していれば、変更なしも正常です。

**安全上の注意と詳細:** 遅延を解消するためにcloseとopenを交互に繰り返さないでください。openでロックが解除されることもありません。Pendingや結果未確認の場合は[スレッドの遅延](#thread-delays)を確認してください。保存済みプレフィックスと手動の名前変更については、[スレッド管理の共通動作](Thread-Lifecycle-ja#reconcile-an-already-active-thread)を参照してください。

<a id="commands-missing-or-permissions-rejected"></a>

## コマンドがない・権限で拒否される

**考えられる原因:** 導入先の相違、コマンド登録の不足・古い定義、実行者の権限喪失、ボットの権限上書き、非公開スレッドへのアクセス・参加不足です。

**確認手順:**

1. 対象サーバーへの導入と、意図したサーバー単位・グローバル範囲への登録を確認します。
2. [コマンド一覧](Command-Reference-ja)から該当コマンドの権限欄を開きます。実行者には、`/config`は「サーバーの管理」、`/thread`は「スレッドの管理」、`/message`は「メッセージの管理」が必要です。実行先のサーバー・チャンネル・スレッドの条件も確認してください。コマンドが表示されるだけでは実行権限は確定しません。
3. WEFT自身の現在のチャンネル権限、権限上書き、スレッド固有のアクセスを別に確認します。スレッド変更には「チャンネルを見る」「スレッドの管理」が必要です。メッセージ送信には、投稿先での送信・埋め込み権限も関係します。保存済み予約の確認では現在のボット送信権限が不要などの違いがあるため、個別コマンドの権限欄を確認してください。

**対処と再試行:** 変更した定義は[コマンド登録手順](Installation-and-Setup-ja#register-commands)で再登録します。権限不足なら修正し、拒否された操作の結果を確認したうえで再実行します。再起動ではコマンド登録されません。回避策としてAdministratorを付与しないでください。アクセスできない対象名は意図的に表示しません。

**解決しない場合:** 保護された名前・認証情報を含めず、コマンドの種類、意図した登録範囲、汎用エラーを運用者へ伝えます。

<a id="bulk-close-skipped-targets"></a>

## 一括クローズで選択した一部のスレッドが処理されません

**考えられる原因:** 実行対象は、候補の中から選択したスレッドだけです。候補表示後の条件・権限変更、別操作による対象の処理、実行中の予約クローズ、実行開始の受付時間切れによって、開始しない対象もあります。一括全体の成功・取消を保証する処理ではありません。

**確認と対処の手順:**

1. 結果件数を保存します。`Selected`は確定時の選択件数であり、候補全件ではありません。選択を解除したスレッドには、その一括操作では何も実行しません。
2. `Skipped`（操作未開始）、`Pending`（開始済みでWEFTが処理継続中）、`Failed or unconfirmed`（完了を確認できていない）を区別します。選択したスレッドの実際の状態をDiscordで確認してください。権限変更後の情報漏洩を防ぐため、件数に対象名は含めません。
3. スキップした対象について、現在のアーカイブ・ロック状態、元の絞り込み条件、実行者とWEFTの現在の「チャンネルを見る」「スレッドの管理」権限を確認します。スレッド内の`/thread status`で、現在の予約クローズも確認してください。別操作が処理中、または予約が実行中でも、新しい試行を開始しない場合があります。
4. 開始済みのPendingは、結果が確定するまで待機します。同時に解決待ちとなる一括操作の対象は、全セッションで最大3件です。確定から5分の受付時間を過ぎると新しい試行を開始しませんが、開始済みの処理は継続します。Pendingについて後から完了通知は送りません。
5. 以前の結果と現在の条件を確認した後でのみ、新しい候補画面を作成します。再起動すると操作画面は無効になり、未開始対象は再開しません。完了済みの変更は残ります。

**安全上の注意:** 一括全体を直ちに繰り返さないでください。失敗・結果未確認でも、Discordが変更されていないとは限りません。クローズの試行で実行待ちの明示予約を取り消した場合、その後のクローズが失敗・Pendingになっても予約は復元しません。新しい候補画面を作成しても、その取消は戻りません。

**詳細:** [一括クローズの結果件数と制限](Bulk-Thread-Close-ja#confirm-and-interpret-the-summary)を参照してください。操作画面自体が拒否される場合は、[操作部品の確認](#bulk-or-list-controls-no-longer-work)を使用してください。

<a id="result-states-and-safe-retry"></a>

## Pending・UNCONFIRMED・PARTIALを再試行前に読み取る

WEFTが処理を継続している場合と、結果を確認できない場合を先に区別してください。Pendingでは待機して観察し、結果未確認では実際の効果と保存された根拠を調べてから次の変更を判断します。

| 結果                              | その結果から分かること                                         | 次の行動                                                                       |
| --------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 確認済み成功                      | 必要な処理と、その完了を裏付ける記録・結果を確認できています。 | 期待する出力を確認します。通知がないだけで再実行しないでください。             |
| 変更なし・すでに完了              | その操作で確認した条件では、新しい変更が不要でした。           | 正常な結果として次へ進みます。                                                 |
| PENDING（処理継続中）             | 最終監査なども含め、WEFTが処理・確認を継続しています。         | 待機して状態を確認します。連続実行で競合させないでください。                   |
| Skipped（スキップ）               | この実行では、その対象の操作を開始していません。               | 新しい選択の前に現在の条件を確認します。クローズ完了を示す結果ではありません。 |
| 確認済み失敗                      | 報告された失敗の事実を確認できています。                       | 原因を修正します。ただし、Discord上の変更に関する注意事項も確認してください。  |
| UNCONFIRMED（結果未確認）         | 処理全体の結果を確定する根拠が不足しています。                 | 再試行・削除の前にDiscordと保存記録を調べます。                                |
| PARTIAL（一部の処理のみ確認済み） | 過去の処理による一部の変更だけを確認できています。             | 元に戻った、新しい内容が残っていると決めつけず、現在の状態を確認します。       |

この表は操作の応答を説明しています。定期実行回の保存状態`PENDING`は実行待ち、`RETRY_PENDING`は許可された送信前再試行の待機です。[予約の表示](Scheduled-Messages-ja#inspect-edit-or-cancel)も確認してください。

保存内容と運用者だけが読める記録は、[確認できる情報](#available-checks)で調べます。それでも結果を確定できなければ、不明なことを再実行の理由にせず、変更を止めて調査してください。

各状態は、確認できている事実が異なります。DBの`CLOSED`だけではアーカイブ成功は確定しません。現在の`CANCELLED`だけでも、結果不明だった特定の取消要求の保存は証明できません。

メッセージ変更を元に戻す処理では、削除確定、確認時に不在、削除・復元の拒否、結果不明を区別します。確認時に不在だったことは、誰が削除したかの証明ではありません。「失敗または結果未確認」はDiscordが無変更だった証明ではありません。

| 予約の応答                 | 確定したこと                                     | 次の行動                                                           |
| -------------------------- | ------------------------------------------------ | ------------------------------------------------------------------ |
| 保存済み・実行登録未確認   | DB保存は確定し、実行登録の確認・修復が必要です。 | 予約を保持してstatusを確認します。登録だけを理由に再作成しません。 |
| 取消済み・キュー停止未確認 | 取消は確定し、キュー停止の確認が必要です。       | 再作成したり、有効な予約へ戻ったと判断したりしません。             |
| 保存・取消自体が未確認     | 変更結果が不明です。                             | 再変更前に現在の状態と正確な運用記録を確認します。                 |

<a id="thread-closeopen-is-still-processing"></a>

## クローズ・状態反映の処理が続いている

**クローズ・状態反映に関わる操作の直後に、同じスレッドを再操作できない場合は、約10分の待機が必要になることを考慮してください。** 連続操作の計画にはその待機を見込み、まず前回の結果を確認します。別のスレッドで操作できても、元の処理が失敗した証明にはなりません。[スレッドのクローズと状態管理](Thread-Lifecycle-ja#delays-and-safe-observation)で、次の操作前に確認する事項を説明しています。10分は目安であり、必ず解除される時間ではありません。

**考えられる原因:** Discordのキュー・レート制限待機、変更結果待ち、状態保存・最終監査の確認です。コマンドの待機時間を超えても、`PENDING`は失敗とは限りません。

**確認手順:**

1. 最初の応答と操作日時を保存します。
2. Discord上の実際の名前・アーカイブ・ロック状態を調べます。
3. [`/thread status`](Commands-Thread-ja#thread-status)で自動クローズ設定と現在の予約クローズを確認します。処理継続中の変更や最終監査をすべて表示するものではありません。
4. 不明なままなら、ホスト運用者が[アプリのログの確認方法](Operations-ja#inspect-operation-logs)に従い、操作日時とスレッドIDを`thread_lifecycle_failed`・`thread_lifecycle_outcome_unknown`やDiscord結果確認の警告に照合します。警告は結果を確認できない理由を調べるもので、元の変更がDiscordで拒否された証明ではありません。さらに調査が必要なら[DB監査履歴](Audit-and-Privacy-ja#audit-storage-reference)を調べます。

**対処と再試行:** WEFTが`PENDING`の処理を続けている間は待機します。10分を超えてから完了する場合もあります。結果未確認なら、現在の状態と運用記録を先に調べます。closeとopenを交互に繰り返したり、10分経過だけを理由に再実行したりしないでください。前回の結果と現在の条件を把握してから、追加操作が必要か判断します。プレフィックス無効化でも制限の回避は保証しません。

**解決しない場合:** 操作の根拠を保持して運用者へ引き継ぎます。再起動しても修復できるとは限らず、起動中のアプリが追跡している未完了処理の情報も失われます。変更を再実行させる目的で再起動を繰り返さないでください。通知の有無だけでは成功・失敗を判断できません。

<a id="an-edit-is-stale-unchanged-or-mismatched"></a>

## 編集が古い・変更なし・不一致

**考えられる原因:** 新しいリビジョン、現在の状態も一致する同一内容、管理対象外・別チャンネルの投稿、現在のアクセス喪失、Discordと保存内容の相違です。

**確認:** 元のチャンネル、WEFT自身の投稿、確定した管理記録を確認します。現在の権限があれば作成者以外も編集できます。応答と実際の投稿を比較します。同一内容でも権限と内容全体の整合性を確認します。

**対処と再試行:** リビジョン競合後は新しいフォームで新内容を確認します。変更なしは正常です。内容不一致なら停止して両方を調べます。WEFTは差を上書きしません。送信・登録・編集・削除・変更前の内容への復元が未確認のまま再送・削除しないでください。`PARTIAL`は元の内容への復元や、新内容が残っていることの証明ではありません。

**解決しない場合:** メッセージID・日時・応答と、版番号が表示されていればその値を保存し、運用者と[管理メッセージ](Managed-Messages-ja#permissions-and-uncertain-outcomes)を確認してください。

<a id="bulk-or-list-controls-no-longer-work"></a>

## 一括・一覧の操作が使えない

**考えられる原因:** 別の利用者、古い版、処理中、有効期限切れ、再起動、権限喪失、不正な操作部品、取得不能です。汎用エラーから原因を1つに決めつけられません。

**確認:** 実行者本人の画面、現在の権限、作成からの時間を確認します。候補画面と一覧の有効期間は固定5分で、操作しても延長しません。

**対処と再試行:** 読取専用の一覧は再実行します。一括操作は開始済み・Pendingの対象を確認してから新しく候補を作ります。50件超過では全体を拒否するため、一部表示と考えず条件を絞ってください。再起動や新しい画面で、以前の変更は戻らず未開始対象も再開しません。

**解決しない場合:** 件数と最初の応答を保持し、以前の結果が不確定なまま一括全体を繰り返さないでください。[一括クローズの結果](Bulk-Thread-Close-ja#confirm-and-interpret-the-summary)を参照してください。

<a id="previews"></a>

<a id="a-preview-is-missing-or-a-button-fails"></a>

## プレビューがない・ボタンが失敗する

**考えられる原因:** モード、未対応・他サーバーのリンク、Message Content Intent、投稿元の送信権限、アーカイブ済み・ロック中の投稿元、非公開投稿元への参加不足、対象のアクセス・年齢判定です。

**確認:** [`link-preview show`](Commands-Config-ja#config-link-preview-show)、Intent、投稿元の閲覧・送信・埋め込み権限を確認します。同じサーバーの対応URLを通常の利用者が新規投稿します。ボタンだけでは対象の存在は証明できません。

**対処と再試行:** 投稿元の設定を直したら、新しい返信で確認します。クリックには現在の利用者・WEFTのアクセスと、年齢制限なしの確認が必要で、所有者・管理者も例外ではありません。既存ラベルは言語変更・再起動で変わらず、`off`・`public-only`では既存ボタンも失敗します。

**解決しない場合:** 汎用エラーは保護されたメッセージの存在を意図的に明かしません。権限を弱めて公開せず、[アクセス規則](Link-Previews-ja#access-privacy-and-copies)を確認してください。

<a id="audit-notifications-missing"></a>

## 監査通知が届かない

Discord通知がないだけでは、操作失敗やDB内の監査記録の不在は判断できません。履歴は別に保存し、通知は1回だけ送信を試みます。再試行や過去分の再送は行いません。

1. 元の操作応答と日時を保持します。実際に[監査対象の変更・失敗](Audit-and-Privacy-ja#what-is-recorded)だったか確認してください。設定の変更なしでは、変更通知を作りません。
2. 「サーバーの管理」権限で[`/config audit-log show`](Commands-Config-ja#config-audit-log-show)を実行します。無効なら送信先はありません。IDがある場合は、実際のテキスト・アナウンスチャンネルの存在と、WEFTの現在の「チャンネルを見る」「メッセージを送信」を確認します。showは保存IDだけを読みます。
3. 保存済み監査があるはずの場合は、運用者が[DB記録](Audit-and-Privacy-ja#audit-storage-reference)と[通知の不達ログ](Operations-ja#inspect-operation-logs)の`audit_notification_delivery`・`outcome`を調べます。クラッシュ・送信失敗で通知だけを失う場合や、一部の失敗監査そのものを保存できない場合があります。通知を発生させる目的で、元の管理操作を繰り返さないでください。

特定できた送信先・権限の問題を直した後、以後の実際の監査対象操作で確認します。過去に届かなかった通知は再送しません。通知を無効にしてもDB監査は続きます。[通知と記録の限界](Audit-and-Privacy-ja#evidence-limits)も参照してください。

<a id="startup-migration-or-readiness-failure"></a>

## 起動・マイグレーション・readinessが失敗する

**考えられる原因:** 非公開設定の不正、PostgreSQL・Discordの停止、未完了のマイグレーション、起動ステップの失敗です。

**確認:** 認証情報を出さず、起動ステップのログ、DB到達性、Discord接続、非公開設定を確認します。[運用](Operations-ja#observe-health-and-logs)でlivenessとreadinessを比較します。

**対処と再試行:** 同じDBのマイグレーションは1プロセスだけ実行し、成功後に起動します。原因を解消してから再起動してください。適用済み履歴の書換えやスケジューラ状態の消去は行いません。復元・移行が未確認または失敗した場合、アプリを停止したままにします。

**解決しない場合:** [運用](Operations-ja)と[バックアップと復旧](Backup-and-Recovery-ja)を使用します。readyでも復旧全体やDiscordとの整合性は確定しません。

<a id="report-a-problem"></a>

## 非公開で根拠を伝える

解決しない再現可能な問題には、ソース版、機密でないコマンド・入力、正確な結果コード、操作日時、関係するID、安全に伏せたログを添えます。トークン、認証情報、非公開本文、設定全体の出力は含めないでください。
