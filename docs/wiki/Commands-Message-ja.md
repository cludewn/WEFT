# メッセージコマンドの詳細

[ホーム](Home-ja) · [コマンド一覧](Command-Reference-ja) · [トラブルシューティング](Troubleshooting-ja) · [English](Commands-Message)

メッセージコマンドの入力と結果を調べるためのページです。今すぐ投稿する場合は[`/message send`](#message-send)、管理メッセージを更新する場合は[`/message edit`](#message-edit)、保存済みの予約を調べる場合は[`/message schedule list`](#message-schedule-list)と[`status`](#message-schedule-status)へ進んでください。

10操作すべてがサーバー内専用で、実行者の現在の「メッセージの管理」権限（`ManageMessages`）が必要です。作成は投稿先、後からの管理は元のチャンネルで行います。スレッドが開いている必要があるか、WEFTにどの権限が必要かは、各項目の「権限と場所」で確認してください。コマンドが表示されているだけでは実行許可になりません。操作結果とエラーは実行者だけに表示します。一連の手順は[管理メッセージ](Managed-Messages-ja)または[予約投稿](Scheduled-Messages-ja)を参照してください。

**構文と操作方法:** 構文のコードブロックはコマンド名と引数を説明する表記で、貼り付けて実行する文字列ではありません。DiscordでWEFTのコマンド候補を選び、引数を指定して実行します。`<...>`や省略可能な引数の`[...]`は入力しません。

- **文字列と選択肢:** 期間、時刻、タイムゾーン、ID、曜日リストは文字列で入力します。`frequency`は「毎日」「毎週」の選択肢から選びます。表示名はDiscordの言語で変わります。`weekdays`は選択欄ではなく、カンマ区切りの文字列入力です。
- **フォーム:** 送信、編集、単発予約・定期投稿の作成、予約内容の編集では、本文のフォームを開きます。フォームを送信すると、投稿や保存内容の変更を依頼します。開くだけでは変更しません。編集時は入力済みの項目全体を確認してください。必須条件と上限は[本文・埋め込みの共通ルール](Managed-Messages-ja#shared-form-rules)を参照してください。
- **ID:** `/message edit`の`message`にはDiscordメッセージIDまたは対応する投稿リンクを指定します。`id`を指定する予約操作では、作成結果か一覧にある予約UUIDを使用します。これらのIDは別のものです。
- **読取と直接の変更:** listとstatusは本文のフォームを開きません。reschedule、recurrence-edit、cancelもスラッシュ引数で直接操作します。一覧の移動は、ページ引数ではなく「前へ」「次へ」ボタンを使用します。

以下の使用例では、具体的な目的に対する入力と実行後の確認を説明します。[Discordでの共通入力方法](Command-Reference-ja#read-syntax)も参照してください。結果未確認や一部の処理のみ確認済みの場合は、繰り返す前に[結果の見方](Troubleshooting-ja#result-states)を確認します。予約の保存と実際の投稿は別の結果です。**リビジョン**は保存内容の版番号で、古いフォームから新しい変更を上書きしないために使います。**実行登録**は、保存予約をスケジューラが処理するための実行準備であり、送信完了ではありません。結果保存とは、Discord操作後の結果をDBへ保存・確認する処理です。[確認できる情報](Troubleshooting-ja#available-checks)に従い、現在の保存内容・実際の投稿・運用者だけが読める履歴を区別してください。

## /message send

**目的:** ボットとして投稿し、管理メッセージとして記録します。

**権限と場所:**

- このサーバーの現在のテキスト・アナウンスチャンネル、または開いている対応スレッドで「メッセージの管理」（`ManageMessages`）が必要です。アクセス可能な非公開スレッドやフォーラム投稿でも使用できます。対象は現在のチャンネルです。WEFTが直前のアクセスを再確認します。
- 送信にはViewChannelとSendMessagesまたはSendMessagesInThreads、明示的な埋め込みにはEmbedLinksも必要です。

**構文:**

```text
/message send
```

**引数:**

スラッシュコマンドの引数はありません。

**使用例:**

後からWEFTで管理できる、簡単なルール確認のお知らせを投稿する場合の例です。

1. 投稿先のチャンネルで、`/message send`を引数なしで実行します。
2. フォームの「本文」に`更新されたサーバールールを確認してください。`と入力します。この例では本文だけを送るため、埋め込みの項目は空欄のままフォームを送信します。
3. 管理メッセージの送信成功が確定したことを確認し、返されたDiscordメッセージIDを控えます。同じチャンネルで実際の投稿も確認してください。

フォームを開くだけでは送信しません。送信や管理登録が結果未確認の場合は、再送・削除の前に[管理メッセージの結果の確認](Managed-Messages-ja#permissions-and-uncertain-outcomes)へ進んでください。

**結果:**

- **フォーム:** 本文・埋め込みの5項目を開きます。送信すると本文、対応する埋め込み1件、または両方を投稿します。
- **確認済み成功:** DiscordメッセージIDとWEFT管理記録が確定します。
- **送信拒否確定:** 未送信です。送信・登録未確認は下記の制約と区別してください。

**制約:**

- フォームを開くだけでは送信しません。[共通の入力制約](Managed-Messages-ja#shared-form-rules)を参照してください。添付、なりすまし、自動メンションはありません。送信未確認でも存在する場合があります。送信済みでも登録がUNCONFIRMEDなら管理記録は未確定で、WEFTは削除していません。
- 送信を取り消すために削除を試みた場合は、削除済み・確認時に不在を区別します。削除拒否・結果不明では確認が必要です。既存の投稿と保存記録を確認してから再送を判断してください。

**関連:** [管理メッセージ](Managed-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message edit

**目的:** 管理メッセージの本文と対応する埋め込み全体を編集します。

**権限と場所:**

- このサーバーの現在のテキスト・アナウンスチャンネル、または開いている対応スレッドでManageMessagesが必要です。対象は同じチャンネルの管理メッセージです。
- WEFTにはViewChannel、ReadMessageHistory、現在の編集可能性が必要で、変更後に明示的な埋め込みがあればEmbedLinksも必要です。現在のDiscord上の内容と保存内容が一致し、変更が不要な場合は、埋め込みを変更しません。送信権限は編集の条件ではありません。

**構文:**

```text
/message edit message:<id-or-link>
```

**引数:**

| 引数      | 必須・任意 | 入力方法・条件                                                                                                                                                                                                    |
| --------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `message` | 必須       | uint64範囲内の17～20桁の正のメッセージID、または現在のサーバー・チャンネルの`https://discord.com/channels/<server-id>/<channel-id>/<message-id>`形式のリンクを文字列で入力します。余分なURL部分は付けられません。 |

**使用例:**

WEFTの管理メッセージとして投稿した、ルール確認のお知らせを更新する場合の例です。

1. 対象の投稿があるチャンネルで、`/message edit`の`message`に実際のDiscordメッセージIDまたは対応するリンクを入力して実行します。
2. 保存内容が入力されたフォームで、「本文」を`投稿前に、更新されたサーバールールを確認してください。`へ変更します。他の項目も確認し、残す埋め込みはその内容を保持してフォームを送信します。
3. 更新または変更なしという結果と、同じDiscord投稿の内容を確認します。既存の投稿を編集する操作であり、別の投稿は作成しません。

フォームが古い場合や、実際の投稿と保存内容が一致しない場合は、そこで操作を止め、[編集と結果未確認の扱い](Managed-Messages-ja#permissions-and-uncertain-outcomes)を確認してください。

**結果:**

- **フォーム:** 保存済み内容を読み込みます。
- **変更・変更なし:** 編集成功時は投稿とリビジョンを1回更新します。現在の状態も一致する同一内容なら変更なしです。
- **削除検知:** Discord上の不在が確定した場合、保存内容とリビジョンを保って`DELETED`を記録します。

**制約:** WEFTが送信し、管理記録が確定し、現在も編集可能な投稿が対象です。作成者以外の権限を持つ管理者も編集できます。古いフォームやDiscordと保存内容の不一致は上書きせず拒否します。編集・記録・復元が未確認なら投稿と記録の両方を調べます。PARTIALは元の内容に戻った証明ではありません。

**関連:** [管理メッセージ](Managed-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message schedule create

**目的:** 現在のチャンネルに管理メッセージを1回送る予約を作成します。

**権限と場所:**

- このサーバーの現在のテキスト・アナウンスチャンネル、または開いている対応スレッドで「メッセージの管理」（`ManageMessages`）が必要です。アクセス可能な非公開スレッドやフォーラム投稿でも使用できます。対象は現在のチャンネルです。
- 予約作成時に、WEFTのViewChannelとSendMessagesまたはSendMessagesInThreads、明示的な埋め込みがあればEmbedLinksを確認します。実際の送信時にもWEFTの現在の権限を再確認します。

**構文:**

```text
/message schedule create [after:<duration>] [at:<YYYY-MM-DD HH:mm>]
```

**引数:**

| 引数    | 必須・任意 | 入力方法・条件                                                                                                                                |
| ------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `after` | 任意       | `after`と`at`のどちらか1つを指定します。`after`には、正の整数と`m`、`h`、`d`のいずれかを1組の文字列で入力します。範囲は1m～365dです。         |
| `at`    | 任意       | WEFTの現在の既定タイムゾーンで、`YYYY-MM-DD HH:mm`形式のASCII 16文字の文字列を入力します。1分後～365日後（1日は24時間）の日時を指定できます。 |

**使用例:**

2時間後のメンテナンス通知を予約する場合の例です。

1. 投稿先のチャンネルで、`/message schedule create`の`after`に`2h`を入力し、`at`は省略して実行します。
2. フォームの「本文」に`まもなく定期メンテナンスを開始します。`と入力し、埋め込みの項目は空欄のままフォームを送信します。
3. 保存が確定した応答で、予約のUUIDと送信日時を控えます。同じチャンネルで[`/message schedule status`](#message-schedule-status)の`id`にそのUUIDを指定し、予約を確認します。
4. 予定日時の後は、実際の投稿を確認します。完了した単発予約のstatusには、結果の投稿リンクが表示される場合があります。

時間の計測は、フォーム送信と直前確認の後に開始します。保存は送信完了ではありません。実行登録待ちの場合も、重複する予約を作らず保存済みの予約を保持してください。

**結果:**

- **フォーム:** 共通の入力項目を開き、送信前には予約を作成しません。
- **保存済み:** 予約IDと送信日時を返します。`after`は送信と直前確認の後から計測します。
- **保存済み・実行登録待ち:** 確定した予約は残り、WEFTが確認・修復します。保存自体が未確認の場合とは異なります。

**制約:**

- Discord上では各引数が任意でも、`after`と`at`のどちらか1つは必要です。両方・両方なし・空入力は拒否します。atは日付不正、DST欠落・重複時刻、秒、オフセット、余分な空白を拒否します。保存UNCONFIRMEDと、保存確定・登録待ちは異なります。通常の再起動時の復旧では、予定日時から60分後ちょうどまでが猶予期間です。
- 再作成は重複排除されず、別予約になり得ます。

**関連:** [単発予約と定期投稿](Scheduled-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message schedule recurring-create

**目的:** 現地時刻とタイムゾーンを保存し、毎日または毎週の定期投稿を作成します。

**権限と場所:**

- このサーバーの現在のテキスト・アナウンスチャンネル、または開いている対応スレッドで「メッセージの管理」（`ManageMessages`）が必要です。アクセス可能な非公開スレッドやフォーラム投稿でも使用できます。対象は現在のチャンネルです。
- 予約作成時に、WEFTのViewChannelとSendMessagesまたはSendMessagesInThreads、明示的な埋め込みがあればEmbedLinksを確認します。実際の送信時にもWEFTの現在の権限を再確認します。

**構文:**

```text
/message schedule recurring-create frequency:<daily|weekly> time:<HH:MM> [weekdays:<weekday-list>] [timezone:<IANA>]
```

**引数:**

| 引数        | 必須・任意 | 入力方法・条件                                                                                                                                                                 |
| ----------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `frequency` | 必須       | 文字列の選択肢から「毎日」（値`daily`）または「毎週」（値`weekly`）を選びます。英語の表示名はdaily・weeklyです。                                                               |
| `time`      | 必須       | `09:30`など、24時間表記の`HH:MM`形式で文字列を入力します。                                                                                                                     |
| `weekdays`  | 任意       | `daily`では省略し、`weekly`では指定します。`mon,tue,wed,thu,fri,sat,sun`から重複しない曜日をカンマ区切りの文字列で入力します。曜日の大文字・小文字と前後の空白は区別しません。 |
| `timezone`  | 任意       | IANA名またはUTCを文字列で入力します。有効な別名も使えますが、数値オフセットは使えません。省略時はフォーム送信時のWEFTの既定値を保存します。                                    |

**使用例:**

毎週月・水・金曜日の日本時間09:30に、サポート状況の報告を依頼する場合の例です。

1. 投稿先のチャンネルで`/message schedule recurring-create`を選びます。`frequency`は「毎週」（値: `weekly`）を選び、`time`に`09:30`、`weekdays`に`mon,wed,fri`、`timezone`に`Asia/Tokyo`を指定して実行します。
2. フォームの「本文」に`本日のサポート状況をこのチャンネルに投稿してください。`と入力し、埋め込みの項目は空欄のまま送信します。
3. 保存が確定した予約のUUIDと初回日時を控えます。同じチャンネルで[`/message schedule status`](#message-schedule-status)の`id`にそのUUIDを指定し、毎週の設定、現地時刻、保存タイムゾーン、現在の実行回を確認します。
4. 実行回の予定日時の後は、Discord上の実際の投稿を確認します。

頻度は選択肢から選び、曜日名は文字列として入力します。定期投稿の保存完了は、その実行回が送信済みであることを意味しません。

**結果:**

- **フォーム:** 共通の入力項目を開きます。
- **保存済み:** 送信すると予約IDと初回日時を持つ定期投稿を1件作成します。各回の成功した投稿は個別の管理メッセージになります。
- **実行登録待ち:** 保存確定した定期投稿は残ります。

**制約:**

- cron式の直接指定、月次、終了日、回数指定には対応しません。dailyでは曜日を省略し、weeklyでは有効な曜日を重複なしで指定します。極端に長いタイムゾーン名は、フォームを識別する情報に収まらず、本文フォームを開けない場合があります。その場合は予約を作成していません。目的の地域に対応する有効な短いIANA名・別名を使い、保存後の日時も確認してください。DST欠落はスキップし、重複時刻は早い方だけ実行します。
- 停止後の復旧では直近の未実行回だけを対象とし、予定日時から15分後ちょうどまでが猶予期間です。作成UNCONFIRMEDなら再試行前に確認します。

**関連:** [単発予約と定期投稿](Scheduled-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message schedule list

**目的:** このチャンネルの終了していない単発予約と定期投稿を一覧表示します。

**権限と場所:** 予約を作成したサーバーとチャンネル（テキスト・アナウンス・対応スレッド）で、現在のManageMessagesが必要です。アーカイブ済みスレッドでも予約の管理はできます。保存された予約の確認・管理に、現在のWEFTの送信権限は不要です。

**構文:**

```text
/message schedule list
```

**引数:**

スラッシュコマンドの引数はありません。

**使用例:**

今後のリマインダーの予約IDを探す場合は、作成したチャンネルで`/message schedule list`を引数なしで実行します。種類、日時、状態、作成者IDを照合し、他のページがある場合は「前へ」「次へ」を使用してください。予約のUUID全体を控え、[`/message schedule status`](#message-schedule-status)の`id`に指定して詳細を確認します。

一覧に本文や終了済みの予約は表示しません。期待する行がない場合は、作成時に控えたIDでstatusを確認し、[届かない予約投稿の調査](Troubleshooting-ja#a-scheduled-post-did-not-appear)へ進んでください。一覧にないだけで取消済みとは判断できません。

**結果:**

- **表示:** 1ページ目から最大10件を表示します。完全な予約ID、作成者ID、種類、状態、日時を示し、本文は出しません。
- **対象:** 単発の`ACTIVE`・`EXECUTING`と終了していない定期投稿を日時・ID順にまとめます。
- **移動:** 前へ・次へボタンを使います。最初のページが空ならボタンはありません。

**制約:**

- ページ指定の引数はありません。ボタンは実行者専用で5分有効、再起動で無効になります。ページ移動ごとに再取得するため、同時変更で行が移動・重複表示され得ます。無効・処理中・古いボタンでは一覧を再実行します。有効期限切れと決めつけないでください。表示不能や取得失敗は予約がないことを意味しません。
- 一覧の操作セッションはプロセス全体で最大128件保持し、上限では新しい一覧表示を拒否します。期限切れでも未完了の処理がある場合は、確定まで枠を占有し得ます。保存可能な予約数の制限ではありません。
- 行を自動的に切り詰めて一部だけ表示することもありません。

**関連:** [単発予約と定期投稿](Scheduled-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message schedule status

**目的:** メッセージ本文を表示せず、予約1件の状態を読み取ります。

**権限と場所:** 予約を作成したサーバーとチャンネル（テキスト・アナウンス・対応スレッド）で、現在のManageMessagesが必要です。アーカイブ済みスレッドでも予約の管理はできます。保存された予約の確認・管理に、現在のWEFTの送信権限は不要です。

**構文:**

```text
/message schedule status id:<schedule-id>
```

**引数:**

| 引数 | 必須・任意 | 入力方法・条件                                                                                                       |
| ---- | ---------- | -------------------------------------------------------------------------------------------------------------------- |
| `id` | 必須       | 作成結果または一覧にある予約UUIDを文字列で入力します。このサーバーと現在のチャンネルに属する予約を指定してください。 |

**使用例:**

保存したリマインダーが届かない場合の例です。

1. 作成したチャンネルで、`/message schedule status`の`id`に実際の予約UUIDを指定して実行します。作成結果または[`/message schedule list`](#message-schedule-list)のIDを使用し、DiscordメッセージIDとは区別してください。
2. 単発予約では状態、予定日時、再試行数を確認します。定期投稿では、現地時刻の繰り返し設定、保存タイムゾーン、現在の実行回の状態も確認します。
3. 完了した単発予約に投稿リンクが表示される場合は、実際の投稿を確認します。status自体は、投稿が現在も存在することを確認するものではありません。

実行中、失敗、送信結果未確認の場合は、代わりの予約を作成する前に[予約投稿の症状別確認](Troubleshooting-ja#a-scheduled-post-did-not-appear)へ進んでください。

**結果:**

- **単発:** 状態、対象、作成者、送信日時、再試行数を表示します。結果IDのある完了予約は投稿リンクも表示します。
- **定期:** 設定全体の状態、繰り返し設定、タイムゾーン、リビジョン、現在の実行回ID・状態、再試行数を表示します。
- **日時:** 実行・再試行中の日時は元の予定日時であり、再試行開始日時ではありません。
- **実行回の状態:** `PENDING`は実行待ち、`EXECUTING`は実行中、`RETRY_PENDING`は許可された送信前再試行の待機です。

**制約:** Discord上の存在確認、実行登録確認、修復は行いません。読取直後にも状態は変わり得ます。不存在・取得不能・不整合を取消確定や失敗確定とは扱いません。必要なら実際の投稿リンクと運用記録を調べてください。

**関連:** [単発予約と定期投稿](Scheduled-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message schedule edit

**目的:** 単発予約または定期投稿の保存済み本文と埋め込みを変更します。

**権限と場所:** 予約を作成したサーバーとチャンネル（テキスト・アナウンス・対応スレッド）で、現在のManageMessagesが必要です。アーカイブ済みスレッドでも予約の管理はできます。保存された予約の確認・管理に、現在のWEFTの送信権限は不要です。

**構文:**

```text
/message schedule edit id:<schedule-id>
```

**引数:**

| 引数 | 必須・任意 | 入力方法・条件                                                                                                       |
| ---- | ---------- | -------------------------------------------------------------------------------------------------------------------- |
| `id` | 必須       | 作成結果または一覧にある予約UUIDを文字列で入力します。このサーバーと現在のチャンネルに属する予約を指定してください。 |

**使用例:**

送信前のメンテナンス通知の本文を変更する場合の例です。

1. 元のチャンネルで[`/message schedule status`](#message-schedule-status)を確認します。単発予約は`ACTIVE`である必要があります。有効な定期投稿も編集できます。
2. `/message schedule edit`の`id`に実際の予約UUIDを指定して実行します。
3. 保存内容が入力されたフォームで、「本文」を`定期メンテナンスを延期しました。`へ変更します。残す埋め込みの項目も確認して保持し、フォームを送信します。
4. 変更または変更なしという結果を確認します。statusでは予約の状態を確認できますが、保存した本文は表示しません。

保存内容を変更する操作であり、送信日時や公開済みの投稿は変更しません。実行・再試行中の定期実行回は取得済みの内容を保持します。結果未確認の場合は、新しい編集フォームを開く前に結果を調べてください。

**結果:**

- **フォーム:** 現在のリビジョンで共通の入力項目を開きます。
- **変更・変更なし:** 内容変更でリビジョンを1回増やします。正規化後の同一内容はリビジョン・監査を増やしません。
- **処理中の定期実行回:** 実行・再試行中の回は以前に取得した内容を保持します。

**制約:** 単発はACTIVEのみで、EXECUTINGや終了状態では編集できません。定期は有効な設定なら実行中も内容を変更できますが、送信済み投稿や実行中の内容を置き換えません。古いフォームは上書きせず拒否します。UNCONFIRMEDなら[確認できる情報](Troubleshooting-ja#available-checks)に従って保存結果を調べてから、新しいフォームを開きます。

**関連:** [単発予約と定期投稿](Scheduled-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message schedule reschedule

**目的:** ACTIVEの単発予約の内容を保ち、送信日時を変更します。

**権限と場所:** 予約を作成したサーバーとチャンネル（テキスト・アナウンス・対応スレッド）で、現在のManageMessagesが必要です。アーカイブ済みスレッドでも予約の管理はできます。保存された予約の確認・管理に、現在のWEFTの送信権限は不要です。

**構文:**

```text
/message schedule reschedule id:<schedule-id> [after:<duration>] [at:<YYYY-MM-DD HH:mm>]
```

**引数:**

| 引数    | 必須・任意 | 入力方法・条件                                                                                                                                |
| ------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`    | 必須       | 作成結果または一覧にある予約UUIDを文字列で入力します。このサーバーと現在のチャンネルに属する予約を指定してください。                          |
| `after` | 任意       | `after`と`at`のどちらか1つを指定します。`after`には、正の整数と`m`、`h`、`d`のいずれかを1組の文字列で入力します。範囲は1m～365dです。         |
| `at`    | 任意       | WEFTの現在の既定タイムゾーンで、`YYYY-MM-DD HH:mm`形式のASCII 16文字の文字列を入力します。1分後～365日後（1日は24時間）の日時を指定できます。 |

**使用例:**

今後の単発リマインダーを、この変更から2時間後へ移動する場合の例です。

1. 元のチャンネルで[`/message schedule status`](#message-schedule-status)を実行し、対象が単発予約で`ACTIVE`であることを確認します。
2. `/message schedule reschedule`の`id`に実際の予約UUID、`after`に`2h`を指定し、`at`は省略して実行します。本文のフォームは開きません。
3. 返された新しい送信日時を確認し、同じIDのstatusで日時を確認します。保存済みの内容は変わりません。

2時間は、元の予定日時への加算ではなく、この操作から計測します。実行登録待ちでも確定した日時変更は保存されています。競合や結果未確認の場合は、確認してから再試行を判断してください。

**結果:**

- **保存済み:** 新しい日時を返します。`after`は古い日時ではなく、この変更操作から計測します。
- **リビジョン:** 同じ日時でもリビジョンを増やし、日時変更を監査します。
- **実行登録待ち:** 確定して保存された変更日時は、そのまま有効です。

**制約:** 作成時と同じ入力・タイムゾーン・DST規則でafter/atのいずれか1つを指定します。EXECUTING・取消済み・終了済みの単発予約は変更できません。定期IDでは拒否し、recurrence-editを案内します。競合やUNCONFIRMEDならstatusを確認してから再試行します。

**関連:** [タイムゾーンと日時指定](Timezones-and-Scheduling-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message schedule recurrence-edit

**目的:** 有効な定期投稿の頻度、現地時刻、曜日、タイムゾーンを変更します。

**権限と場所:** 予約を作成したサーバーとチャンネル（テキスト・アナウンス・対応スレッド）で、現在のManageMessagesが必要です。アーカイブ済みスレッドでも予約の管理はできます。保存された予約の確認・管理に、現在のWEFTの送信権限は不要です。

**構文:**

```text
/message schedule recurrence-edit id:<schedule-id> frequency:<daily|weekly> time:<HH:MM> [weekdays:<weekday-list>] [timezone:<IANA>]
```

**引数:**

| 引数        | 必須・任意 | 入力方法・条件                                                                                                                                                                 |
| ----------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`        | 必須       | 作成結果または一覧にある予約UUIDを文字列で入力します。このサーバーと現在のチャンネルに属する予約を指定してください。                                                           |
| `frequency` | 必須       | 文字列の選択肢から「毎日」（値`daily`）または「毎週」（値`weekly`）を選びます。英語の表示名はdaily・weeklyです。                                                               |
| `time`      | 必須       | `09:30`など、24時間表記の`HH:MM`形式で文字列を入力します。                                                                                                                     |
| `weekdays`  | 任意       | `daily`では省略し、`weekly`では指定します。`mon,tue,wed,thu,fri,sat,sun`から重複しない曜日をカンマ区切りの文字列で入力します。曜日の大文字・小文字と前後の空白は区別しません。 |
| `timezone`  | 任意       | IANA名またはUTCを文字列で入力します。有効な別名も使えますが、数値オフセットは使えません。省略時はこの定期投稿の保存済みタイムゾーンを保持します。                              |

**使用例:**

保存済みタイムゾーンを保持したまま、定期のお知らせを毎日10:00に変更する場合の例です。

1. 元のチャンネルで、対象の定期投稿を[`/message schedule status`](#message-schedule-status)で確認します。
2. `/message schedule recurrence-edit`の`id`に実際の予約UUIDを指定します。`frequency`は「毎日」（値: `daily`）、`time`は`10:00`とし、`weekdays`と`timezone`は省略して実行します。
3. 変更または変更なしという結果を確認します。statusで毎日の設定、現地時刻、保持したタイムゾーンを確認してください。

本文のフォームを開かず、繰り返し設定を変更します。実行・再試行中の回は以前の設定を保持し、その処理が終了した後の回に新しい設定を適用します。

**結果:**

- **変更なし:** 正規化後に同じならリビジョンと現在の実行回を変更しません。
- **変更:** リビジョンを増やし、待機中の回を置換します。保存済みでも実行登録待ちの場合があります。
- **処理中:** 実行・再試行中の回は以前の設定を保持し、終了後に次の回を準備します。

**制約:** 単発IDにはrescheduleを使います。タイムゾーン省略時は現在のサーバー既定値ではなく、この定期投稿の保存値を保持します。dailyでは曜日省略、weeklyでは必須です。実行中の回の時刻は変わりません。競合やUNCONFIRMEDならstatusで確認してから再試行します。

**関連:** [単発予約と定期投稿](Scheduled-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)

## /message schedule cancel

**目的:** 単発予約を取り消すか、定期投稿の以後の実行回を停止します。

**権限と場所:** 予約を作成したサーバーとチャンネル（テキスト・アナウンス・対応スレッド）で、現在のManageMessagesが必要です。アーカイブ済みスレッドでも予約の管理はできます。保存された予約の確認・管理に、現在のWEFTの送信権限は不要です。

**構文:**

```text
/message schedule cancel id:<schedule-id>
```

**引数:**

| 引数 | 必須・任意 | 入力方法・条件                                                                                                       |
| ---- | ---------- | -------------------------------------------------------------------------------------------------------------------- |
| `id` | 必須       | 作成結果または一覧にある予約UUIDを文字列で入力します。このサーバーと現在のチャンネルに属する予約を指定してください。 |

**使用例:**

不要になったリマインダーや、定期のお知らせの今後の投稿を止める場合の例です。

1. 元のチャンネルで[`/message schedule status`](#message-schedule-status)を使い、対象の予約と実行開始の有無を確認します。
2. `/message schedule cancel`の`id`に実際の予約UUIDを指定して実行します。
3. 取消が確定したか、すでに取消済みか、単発の送信が実行中のため取り消せないかを読み分けます。取消が確定したら、同じIDのstatusを確認します。

キュー停止待ちでも、確定した取消は取消済みのままです。公開済みの投稿の削除や、実行中の定期投稿の強制停止は行いません。取消自体が結果未確認なら、再び変更する前に[結果の見方](Troubleshooting-ja#result-states)を確認してください。

**結果:**

- **単発:** `ACTIVE`を`CANCELLED`にし、取消済みなら変更なしです。`EXECUTING`は取り消せません。
- **定期:** 将来の回を止め、待機中・再試行待ちをスキップします。実行中の処理は残ります。
- **キュー停止未確認:** 確定した取消は取消済みです。

**制約:** 送信済み投稿を削除せず、実行中の外部送信を強制停止しません。完了・失敗した単発予約は終了済みです。リビジョン競合や取消UNCONFIRMEDならstatusで確認します。一覧にないだけで取消済みと判断しないでください。

後から定期投稿が届いた場合は、取消の再実行や代替予約の作成の前に、[取消後の投稿の確認手順](Troubleshooting-ja#post-after-recurring-cancel)を使用してください。

**関連:** [単発予約と定期投稿](Scheduled-Messages-ja) · [結果の見方](Troubleshooting-ja#result-states)
