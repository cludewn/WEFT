# 単発予約と定期投稿

[ホーム](Home-ja) · [コマンド一覧](Command-Reference-ja) · [トラブルシューティング](Troubleshooting-ja) · [English](Scheduled-Messages)

予約投稿は、管理者がオンラインでなくても、後でWEFTからお知らせを送信する機能です。1回のリマインダーには[単発予約](#create-a-one-time-post)、毎日・毎週のお知らせには[定期投稿](#create-a-recurring-post)を使います。定期投稿の1回分の送信を**実行回**と呼び、成功した投稿はそれぞれ個別の[管理メッセージ](Managed-Messages-ja)になります。

作成済みの予約がある場合は、[予約IDと状態を確認](#inspect-edit-or-cancel)してから[変更](#change-a-reservation)または[取消](#cancel-a-reservation)へ進んでください。投稿が届かない場合は、[予約投稿の調査手順](Troubleshooting-ja#a-scheduled-post-did-not-appear)から確認できます。

<a id="before-creating"></a>

## 投稿先と時刻を確認する

**投稿先の**サーバー内テキスト・アナウンスチャンネル、または開いている対応スレッドで作成コマンドを実行します。投稿先チャンネルを指定する引数はありません。実行者に「メッセージの管理」、WEFTに閲覧・送信権限、明示的な埋め込みには「埋め込みリンク」が必要です。送信時にもWEFT自身の現在のアクセスを再確認します。送信のための非公開スレッドへの参加やアーカイブ解除は行いません。

現地日時や定期投稿には、先に[WEFTの既定タイムゾーン](Timezones-and-Scheduling-ja)を確認してください。返された送信日時は、Discordの各閲覧者のクライアント側タイムゾーンで表示され、入力時のタイムゾーンとは異なる場合があります。

**予約の作成は、後で実行する処理の保存であり、投稿の送信ではありません。** 作成コマンドを別々に実行すると予約が重複する場合があります。作成結果が不確定なら、[保存された予約とDiscordを確認](#save-the-schedule-id)してから再作成を判断してください。

<a id="create-a-one-time-post"></a>

## 1回のリマインダーを予約する

2時間後にメンテナンスのお知らせを投稿する例です。

1. 投稿先で[`/message schedule create`](Commands-Message-ja#message-schedule-create)を選びます。`after`に`2h`を入力し、`at`は指定せずに実行します。
2. フォームでお知らせの本文、埋め込み、または両方を入力します。入力方法は[共通の入力項目](Managed-Messages-ja#shared-form-rules)を参照してください。フォームを送信すると予約を保存します。開いただけでは作成しません。
3. 応答の**予約IDと送信日時**を確認し、[IDを控えて保存済み予約を確認](#save-the-schedule-id)します。この応答は保存の確認であり、投稿の送信成功を示すものではありません。

`2h`はフォーム送信と直前確認の後から計測するため、フォーム入力中に短くなりません。相対時間は、正の整数1つと単位`m`・`h`・`d`のいずれか1つで指定します。

日付を指定する場合は、同じコマンドで`after`を省略し、`at`に未来の現地日時を`YYYY-MM-DD HH:mm`形式で引用符を付けずに入力します。`2026-11-01 19:30`は書式の例なので、実際には有効な未来の日時を選んでください。**`after`と`at`は、どちらか1つだけ指定します。** 両方式とも1分～365日（1日は24時間）で指定できます。拒否される日時は[日時入力とDST](Timezones-and-Scheduling-ja)で確認してください。

<a id="create-a-recurring-post"></a>

## 毎日・毎週の投稿を予約する

東京時間で月・水・金の09:30にお知らせを投稿する例です。

1. 投稿先で[`/message schedule recurring-create`](Commands-Message-ja#message-schedule-recurring-create)を選びます。`frequency`は自由入力ではなく、**「毎週」を選択**します（値: `weekly`）。`time`に`09:30`、`weekdays`に`mon,wed,fri`、`timezone`に`Asia/Tokyo`を入力して実行します。
2. [共通の内容フォーム](Managed-Messages-ja#shared-form-rules)でお知らせの本文・埋め込みを入力して送信します。フォームを送信するまでは定期投稿を作成しません。
3. 応答の**予約IDと初回の送信日時**を確認します。[IDを控えてstatusを実行](#save-the-schedule-id)し、頻度・曜日・現地時刻・保存タイムゾーン・現在の実行回を確認します。

毎日なら`frequency`で「毎日」（値: `daily`）を選び、`weekdays`を省略します。`time`は24時間制の`HH:MM`で指定します。毎週の`weekdays`は、`mon,tue,wed,thu,fri,sat,sun`から重複しない曜日をカンマで区切って入力する文字列です。

作成時には、明示したIANAタイムゾーン、または`timezone`省略時はフォーム送信時のWEFT既定値を保存します。以後の既定値変更では定期投稿は移動しません。夏時間（DST）で存在しない現地時刻の回はスキップし、2回現れる時刻は早い方だけを使います。[タイムゾーンの例](Timezones-and-Scheduling-ja#dst-gaps-and-overlaps)を参照してください。

月次、cron式の直接指定、任意の間隔、開始日・終了日、回数指定には対応しません。入力条件は[コマンド詳細](Commands-Message-ja#message-schedule-recurring-create)で確認できます。

<a id="save-the-schedule-id"></a>

## 予約IDを控え、作成結果を確認する

予約の保存と実行準備は別です。**実行登録**とは、保存した予約を予定日時にWEFTのスケジューラが処理できるよう、実行指示を登録することです。保存確定後に登録未確認と表示されても、保存失敗という意味ではありません。IDを控え、WEFTによる実行指示の確認・修復を待ちます。list・statusは登録自体を検証しないため、期限を過ぎたままなら[調査手順](Troubleshooting-ja#a-scheduled-post-did-not-appear)へ進んでください。

どちらの種類でも、**完全な予約ID・投稿先・返された送信日時**を控えてください。予約IDは予約を識別するもので、Discordの投稿IDではありません。定期投稿は全体で1つの予約IDを使います。状態確認・変更・取消に使うほか、有効な予約の一覧から消えた後も、このIDで確認します。

| 作成応答                 | 確認と対処                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| ID・日時付きの保存済み   | IDを控え、次のstatusで保存日時と状態を確認します。                                               |
| 保存済み・実行登録未確認 | DB保存は確定し、WEFTが実行登録を確認・修復できます。登録修復だけを目的に再作成しないでください。 |
| 保存未確認               | 保存成功・失敗のどちらも未確定です。別予約を作る前にlist・statusとDiscordを確認します。          |

応答でIDを確認できなかった場合は、元のチャンネルの一覧で保存済み予約を調べます。一覧にないだけでは、作成失敗や未送信とは判断できません。不明なままの場合は[予約投稿の調査手順](Troubleshooting-ja#a-scheduled-post-did-not-appear)に進んでください。

<a id="inspect-edit-or-cancel"></a>

## 予約を探して保存状態を確認する

一覧・状態確認・変更・取消は、**作成したサーバー・チャンネル**で、現在の「メッセージの管理」権限を使って実行します。その権限を持つ管理者なら、作成者以外も管理できます。対応スレッドはアーカイブ後も予約管理ができ、保存済み予約の管理にWEFTの現在の送信権限は不要です。

作成者の脱退やロール喪失では予約は停止しません。送信時はWEFT自身の現在のアクセスを確認し、作成者の現在のロールは再確認しません。

<a id="find-the-schedule-id"></a>

### IDを探してstatusを実行する

1. 予約IDを控えている場合は手順3へ進みます。不明な場合は、元のチャンネルで[`/message schedule list`](Commands-Message-ja#message-schedule-list)を**引数なし**で実行します。終了していない予約を1ページ最大10件表示し、本文は出しません。利用可能な場合は「前へ」「次へ」ボタンで移動します。
2. 確認したい予約の完全なIDをコピーします。完了・取消済みの予約は一覧に表示しないため、控えておいたIDで確認します。
3. [`/message schedule status`](Commands-Message-ja#message-schedule-status)を選び、`id`に実際の予約IDを入力して実行します。投稿先・保存日時・状態を確認します。定期投稿は繰り返し設定・保存タイムゾーンに加え、現在の実行回を別に確認します。

| 対象         | 状態の読み方                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------- |
| 単発予約     | `ACTIVE`は実行待ち、`EXECUTING`は実行開始済みです。                                           |
| 定期投稿全体 | 予約全体の状態です。現在の実行回の状態は別に確認します。                                      |
| 定期の実行回 | `PENDING`は実行待ち、`EXECUTING`は実行中、`RETRY_PENDING`は許可された送信前再試行の待機です。 |

これらは予約・実行回の保存状態です。スレッド操作の応答`PENDING`は、WEFTが処理・確認を継続していることを示します。list・statusは保存した本文を表示せず、現在のDiscordメッセージの存在や実行登録も検証しません。再試行中の定期投稿の表示日時は、元の予定日時であり、次の再試行開始日時ではありません。

ボタンを使用できなくなった場合は一覧を再実行してください。取得失敗は空の一覧ではありません。制限は[ボタンの有効期間と同時変更](#button-lifetime-and-concurrent-changes)で説明します。

<a id="change-a-reservation"></a>

## 内容・日時を変更する

次の各操作では`id`に実際の予約IDを指定します。単発予約は`ACTIVE`の間だけ変更でき、実行中・終了済みは変更できません。予約を変更しても、送信済み投稿は編集しません。

<a id="edit-future-content"></a>

### 今後の本文・埋め込みを変更する

送信前にお知らせの内容を訂正する例です。

1. [`/message schedule edit`](Commands-Message-ja#message-schedule-edit)を選び、`id`に予約IDを入力して実行します。単発予約・定期投稿のどちらにも使えます。
2. フォームの保存済み本文・埋め込みを変更して送信します。
3. 応答で、変更の保存または変更なしが確定したかを確認します。statusには本文を表示しません。結果が未確認の場合や他の編集と競合した場合は、[現在の予約を確認してから再試行を判断](#concurrent-edits-and-execution)してください。

実行・再試行中の定期実行回は、取得済みの本文を保持します。本文の変更でその実行回を置き換えることはありません。

<a id="move-a-one-time-send"></a>

### 単発の送信日時を変更する

1. [`/message schedule reschedule`](Commands-Message-ja#message-schedule-reschedule)を選びます。この操作から2時間後へ変更する場合は、`id`に予約ID、`after`に`2h`を入力し、`at`を省略して実行します。代わりに、前述の現地日時形式で`at`だけを使うこともできます。
2. 応答の新しい送信日時を確認し、同じ`id`で`/message schedule status`を実行して保存日時と状態を確認します。

このコマンドは単発予約に使います。日時変更の保存が確定し、実行登録だけが未確認の場合、保存済みの変更は有効で、WEFTが実行登録を修復できます。

<a id="change-repeat-settings"></a>

### 定期投稿の曜日・時刻・タイムゾーンを変更する

有効な毎週の定期投稿を、毎日10:00の投稿へ変更する例です。

1. [`/message schedule recurrence-edit`](Commands-Message-ja#message-schedule-recurrence-edit)を選びます。`id`に予約IDを入力し、`frequency`で「毎日」（値: `daily`）を選び、`time`に`10:00`を入力して`weekdays`を省略します。保存タイムゾーンを維持する場合は`timezone`を省略し、変更する場合はIANAタイムゾーン名を入力します。
2. 応答を読み、同じ`id`で`/message schedule status`を実行します。保存された繰り返し設定・タイムゾーン・現在の実行回を確認します。

繰り返し設定の変更は待機中の回を置き換えます。実行・再試行中の回は取得済み設定を保持し、その終了を待って新しい設定で以後の回を準備します。編集成功は、処理中の送信が変更されたことを意味しません。

<a id="cancel-a-reservation"></a>

## 今後の投稿を取り消して確認する

1. 元のチャンネルで[`/message schedule cancel`](Commands-Message-ja#message-schedule-cancel)を選び、`id`に実際の予約IDを入力して実行します。
2. 取消確定・取消済み・拒否・未確認のどれを示す応答かを確認します。その後、同じ`id`で`/message schedule status`を実行し、保存状態を確認します。一覧から消えただけでは取消確定と判断しないでください。

**取消は送信済み投稿の削除や、実行中の外部送信の強制停止を行いません。** 単発の`EXECUTING`は取消不可です。定期の取消は待機・再試行待ちをスキップし、以後の実行回を止めますが、すでに実行中の回は送信を完了する場合があります。

取消後に定期投稿が届いた場合は、再び設定を変更する前に[取消応答と実行中だった回を照合](Troubleshooting-ja#post-after-recurring-cancel)してください。後から届いた投稿だけでは、取消失敗とは判断できません。

キュー停止が未確認でも、確定した取消は取消済みです。これは取消自体が未確認の場合とは異なります。後で取得した保存状態だけでは、結果が不確定だった取消要求の成功を証明できません。結果が不明な場合は[予約と投稿先を調査](Troubleshooting-ja#a-scheduled-post-did-not-appear)してください。

<a id="read-the-status-and-verify-delivery"></a>

## 予定日時を過ぎたら実際の投稿を確認する

1. 元のチャンネルで`/message schedule status`の`id`に控えておいた予約IDを入力して実行します。
2. 完了した単発予約は、結果の投稿リンクがあれば開き、実際の投稿を確認します。定期投稿は、確認したい実行回の投稿を投稿先で確認します。statusは全投稿の履歴ではなく、定期投稿全体と現在の実行回の状態を表示します。
3. 投稿が見当たらない場合や結果が不明な場合は、代替予約を作る前に[予約投稿の調査手順](Troubleshooting-ja#a-scheduled-post-did-not-appear)を確認してください。作成の保存成功、定期投稿が有効なこと、一覧に行がないことだけでは送信成功とは判断できません。

成功した投稿はそれぞれ個別の[管理メッセージ](Managed-Messages-ja)になります。送信済み投稿を変更したい場合は、予約の編集ではなく、そのガイドの操作を使ってください。

**結果未確認は、未送信が確定した状態ではありません。** WEFTは送信された可能性のある処理を、結果未確認のまま遅延再送し続けません。代替予約を作る前にDiscordを確認してください。重複送信の可能性が残る理由は[再試行と再起動の規則](#uncertain-sends)で説明します。

<a id="concurrent-edits-and-execution"></a>

## 詳細: 同時編集と実行中の変更

**リビジョン**は保存内容の版番号で、途中の変更を検知するために使います。フォームは開いた時点の版を覚えているため、同時編集では新しい内容を上書きせず古いフォームを拒否します。編集が競合した場合はstatusで現在の予約を確認し、新しい編集フォームを開いて保存内容を読みます。この時点ではフォームを送信しません。結果未確認の場合は、[確認できる情報](Troubleshooting-ja#available-checks)に従って調べてから次の変更を送信してください。本文変更はリビジョンを増やし、正規化後に同じなら変更なしです。単発の日時変更は、同じ日時でもリビジョンを増やし監査します。

有効な定期投稿は、実行回の実行・再試行中にも変更できます。その回は取得済みの内容・設定を保持します。繰り返し設定の変更は待機中の回を置き換え、実行・再試行中なら終了を待って以後の回を準備します。正規化後の設定が完全に同じなら変更しません。

<a id="button-lifetime-and-concurrent-changes"></a>

## 詳細: 一覧ボタンの有効期間と同時変更

- 一覧のボタンは実行者専用で、作成から5分間有効です。再起動すると無効になり、ページ移動で有効期間は延長しません。
- ページ移動ごとに再取得します。同時変更で行が別のページへ移動・重複表示される場合があります。
- 取得失敗は空の一覧ではありません。ボタンを使用できなくなった場合は一覧を再実行してください。
- 保存された予約とは別に、一覧の操作セッションをプロセス全体で最大128件保持し、満杯なら新しい一覧表示を拒否します。期限切れでも未完了の処理があれば、確定まで枠を保持する場合があります。

<a id="late-work-restart-and-retries"></a>

## 詳細: 遅延と再起動後の動作

| 猶予・有効期間の規則                                                          | 期間（分） | 計測の基準・適用条件                                                 |
| ----------------------------------------------------------------------------- | ---------- | -------------------------------------------------------------------- |
| <!-- fact:one-time-grace --> 単発予約の期限超過時の猶予                       | 60         | 予定日時から60分後ちょうどまでを含みます。                           |
| <!-- fact:recurring-grace --> 定期投稿で直近の未実行回を送る猶予              | 15         | 予定日時から15分後ちょうどまでを含みます。                           |
| <!-- fact:recurring-retry-lifetime --> 定期投稿の安全な送信前再試行の有効期間 | 15         | 初回試行から15分後ちょうどまでを含みます。未実行回の猶予とは別です。 |

| 再試行の規則                                           | 上限（回） | 回数の扱い                                               |
| ------------------------------------------------------ | ---------- | -------------------------------------------------------- |
| <!-- fact:message-retries --> 安全な送信前再試行の上限 | 3          | 再試行回数を保存するため、再起動してもリセットしません。 |

例えば、通常の復旧で単発の予定日時から60分後ちょうどなら猶予内です。それを超えると古い内容を送らず失敗にします。定期は直近の適用可能な未実行回だけを検討し、猶予内ならその1回を送る場合があります。古い回はスキップ範囲として記録し、直近も猶予外なら未来へ進みます。停止中の全回を再送しません。

確認・修復は前回の終了から60秒空けて実行します。起動時復旧、Discord待機、権限変更、アーカイブ済みの対象により、送信できない・遅れる場合があります。正確な秒の実行は保証しません。

<a id="uncertain-sends"></a>

## 詳細: 再試行と送信結果未確認

安全な送信前再試行は、Discordメッセージが作成される可能性のある要求を送る前に限ります。回数は再起動後も保持します。定期の再試行有効期間は初回試行から計測し、未実行回の猶予とは別です。

送信が不確定な場合、元の要求と対応付けて重複を減らしながら、直ちに最大1回再試行する場合があります。これは自動処理で、利用者が内部識別子を指定する必要はありません。以後に結果を確認せず遅延再送を繰り返しません。重複低減は厳密な1回限りの送信保証ではありません。

起動時には、中断された`EXECUTING`の単発送信と定期実行回を`EXECUTION_INTERRUPTED_UNCONFIRMED`として再送せず終了させます。**代替予約を作る前にDiscordを調べてください。** 症状別の[予約投稿の調査手順](Troubleshooting-ja#a-scheduled-post-did-not-appear)、[コマンド詳細](Commands-Message-ja)、[復元時のリスク](Backup-and-Recovery-ja)も参照してください。
