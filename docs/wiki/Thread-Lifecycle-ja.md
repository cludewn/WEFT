# スレッドのクローズと状態管理

[ホーム](Home-ja) · [コマンド一覧](Command-Reference-ja) · [トラブルシューティング](Troubleshooting-ja) · [English](Thread-Lifecycle)

WEFTのクローズは、終了した議論のスレッドをアーカイブし、有効な場合は名前に`[CLOSED]`などのクローズ用プレフィックスを付ける操作です。例えば、解決したサポートスレッドの名前を`Login help`から`[CLOSED] Login help`に変更し、アーカイブできます。

<a id="close-and-archive"></a>

## クローズ・アーカイブ・ロックの関係

| 操作                      | 結果                                                                                                                             |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| WEFTのクローズ            | ロックや削除をせずアーカイブし、有効な場合は適用対象のクローズ用プレフィックスを付けます。                                       |
| Discordでのアーカイブ解除 | スレッドを再び開いた状態にします。ロックされていないアーカイブ済みスレッドは、Discordでの利用によって開く場合もあります。        |
| `/thread open`            | **すでに開いている**スレッドの状態をWEFTへ反映し、該当する保存済みプレフィックスを除去します。アーカイブやロックは解除しません。 |

クローズは、利用者がロックされていないスレッドを再び開くことを防ぎません。ロック中のスレッドはクローズを拒否します。以後の参加を制限したい場合、WEFTのクローズだけではその制限になりません。

<a id="before-closing"></a>

## 操作前の確認

対応する公開・アナウンススレッド、アクセス可能な非公開スレッド、フォーラム投稿で使用できます。実行者とWEFTの両方に、現在の「チャンネルを見る」と「スレッドの管理」権限が必要です。非公開スレッドにはWEFTがすでにアクセスできる必要があり、アクセスできないスレッドへ自動参加しません。

有効な手動クローズは、待機中の[予約クローズ](Scheduled-Thread-Close-ja)を取り消してからクローズを試みます。その後にクローズが失敗しても取消は残ります。残したい予約がないか、実行前に確認してください。

<a id="close-one-thread"></a>

## スレッドをクローズして結果を確認する

1. 対象のスレッドに移動します。
2. `/thread close`を引数なしで実行します。
3. WEFTの応答と、Discord上の実際のアーカイブ状態・名前を確認します。

「スレッドを閉じました。」「スレッドはすでに閉じています。」という確認済みの応答は、正常な処理結果です。繰り返してもプレフィックスを重複付加しません。プレフィックスが無効なら名前は変わらないため、名前だけで成功を判断しないでください。

`PENDING`（WEFTが処理・結果確認を継続中）なら待機します。結果未確認なら、現在の状態を調べてから再試行してください。詳しくは[遅延と競合](#delays-and-safe-observation)を参照してください。

<a id="reconcile-an-already-active-thread"></a>

## スレッドを再利用して状態を反映する

1. Discordでスレッドのアーカイブを解除します。`/thread open`は**この操作を行いません**。
2. WEFTがアーカイブ解除を検知し、保存済みプレフィックスを除去済みか確認します。
3. 必要なら、すでに開いている対象スレッド内で`/thread open`を引数なしで実行し、応答を確認します。

該当する保存済みの先頭プレフィックスを1つ除去し、必要に応じて管理記録を更新します。WEFT状態だけの更新や変更なしも正常です。管理記録のない対応スレッドでも、開いていれば変更なしとして受け付けます。予約クローズの取消や自動クローズの除外設定の変更は行いません。

<a id="saved-prefixes-and-manual-names"></a>

## 保存済みプレフィックスが以後の操作に与える影響

空でないプレフィックスは、後ろに半角空白を1つ付けて追加します。WEFTはクローズ時の選択を保存し、プレフィックスを使用しなかった場合も記録します。開いた状態がWEFTへ反映されるまで、設定変更や結果確認待ちの間もこの選択を保持します。**保存記録だけではDiscordのアーカイブ成功は確認できません。**

| 操作の順序                                                                    | 開いた状態を反映したときの結果                        |
| ----------------------------------------------------------------------------- | ----------------------------------------------------- |
| `[CLOSED]`でクローズし、プレフィックスを無効にしてからDiscordでアーカイブ解除 | 保存済みの先頭の`[CLOSED] `が残っていれば除去します。 |
| プレフィックスなしでクローズし、`[DONE]`を有効にしてからアーカイブ解除        | 名前を変更しません。                                  |
| 手動で名前を変更し、保存済みプレフィックスが先頭からなくなる                  | 古い名前に戻さず、現在の名前を保持します。            |

開いた状態がWEFTへ反映された後で再びクローズすると、その時点のクローズ用プレフィックス設定が適用されます。

保存済みプレフィックスと区切りの空白以外の手動変更は保持します。プレフィックスが空でない場合は、100 Unicodeコードポイントの名前制限に収めるため、末尾を切り詰める場合があります。openは切られた文字列を復元しません。プレフィックスを使用しない場合は、先頭空白も含めて名前をそのまま保持し、トリムや切り詰めを行いません。設定変更だけでは既存のスレッド名を変更しません。

<a id="delays-and-safe-observation"></a>

## 遅延・競合と安全な確認

**同じスレッドでクローズ・状態反映に関わる操作を短時間に繰り返す場合は、約10分の待機が必要になることを考慮してください。** 別のスレッドでは操作できても、直前に操作したスレッドでは次の操作が進まない場合があります。通常の運用や動作確認で、クローズと`/thread open`を連続して繰り返すことは避けてください。操作できない場合は、応答と実際の状態を確認し、追加操作が必要かを判断します。

**約10分**は操作計画の目安であり、その時間で必ず操作可能になるという保証ではありません。次の操作の前に、前回の応答、実際のスレッド状態、未完了の処理を確認してください。すべてのコマンドに同じ待機が必要とは限りません。この注意の適用範囲は[技術的な補足](#same-thread-wait-background)で説明します。

- Discordのレート制限待機も遅延の原因になり得ますが、経過時間だけでは原因を特定できません。
- WEFTのDiscordクライアントはDiscordのレート制限に従って待機します。プレフィックス無効時もアーカイブ要求に名前を含むため、無効化による回避は保証しません。
- これとは別に、`PENDING`はDiscord上の変更、状態保存、監査確認の継続を含みます。WEFTが処理を続け、同じスレッドへの競合する変更を防いでいるため、後から完了する場合があります。10分経過しても、完了や操作制限の解除を確認したことにはなりません。結果未確認の場合も、時間を決めて再実行せず、先に調査してください。
- 予約の`ACTIVE`は実行待ち、`EXECUTING`は実行開始済みです。実行中の予約や取消未確認の場合は、手動クローズを開始しません。確定した取消は、その後のクローズが失敗・処理継続中でも戻りません。

処理を進める目的でcloseとopenを交互に繰り返さないでください。[`/thread status`](Commands-Thread-ja#thread-status)は自動クローズ設定と現在の予約クローズを示すもので、**処理中のクローズや状態反映をすべて表示するものではありません**。応答と実際の名前・アーカイブ状態を照合し、[調査手順](Troubleshooting-ja#thread-delays)へ進んでください。監査通知がないだけでは失敗と判断できません。

<a id="same-thread-wait-background"></a>

## 技術的な補足: 同一スレッドでの待機

Discord上で同じスレッドへのクローズ・状態反映に関わる操作を繰り返した際に、約10分の待機が必要になった例があります。その間も別のスレッドは操作でき、待機後には元のスレッドでも操作できました。このため連続操作には待機を見込む必要がありますが、制限の原因や解除時刻までは分かっていません。WEFTに固定10分の内部クールタイムはなく、すべてのコマンドへ同じ制限が適用されると確認できているわけではありません。処理・結果確認が未完了の間にWEFTが競合変更を防ぐ仕組み（`PENDING`）とは別です。操作判断には[上記の確認手順](#delays-and-safe-observation)を使用してください。
